# СР3. Асинхронність на практиці: послідовно чи паралельно

## Використані адреси
- `https://jsonplaceholder.typicode.com/posts/1`
- `https://jsonplaceholder.typicode.com/users/1`
- `https://jsonplaceholder.typicode.com/todos/1`

Додаткові перевірки помилок і таймаутів:
- неіснуючий шлях `https://jsonplaceholder.typicode.com/nonexistent-endpoint-999999` (повертає `HTTP 404`, але інші 3 запити виконуються успішно);
- перевірка тайм-ауту (`Request timeout after 1ms`), де помилка обробляється для кожного запиту окремо і не робить неперехопленого падіння.

## Результати вимірювань (мс)

| Режим | Запуск 1 | Запуск 2 | Запуск 3 | Середнє |
|---|---|---|---|---|
| Послідовно (`sequential`) | 152.76 | 71.24 | 78.42 | 100.81 |
| Паралельно (`parallel`) | 58.35 | 27.77 | 25.16 | 37.09 |

## Висновки
- **Паралельне завантаження** доцільне, коли запити незалежні один від одного і потрібно отримати кілька відповідей швидше: затримки очікування мережі перекриваються, тому середній час склав `37.09 мс` проти `100.81 мс` при послідовному запуску.
- **Послідовне завантаження** потрібне, коли наступний запит залежить від даних попереднього (наприклад, спочатку отримати ID користувача, а потім його дані), коли API обмежує кількість одночасних запитів або коли хочеться зменшити пікове навантаження на сервер чи з'єднання.
